## 2026-11-13 — Sv39 根页表的叶子项按 1 GiB 页翻译

### 现象

裸机汇编在根页表项 2 写入覆盖 `[0x8000_0000, 0xC000_0000)` 的身份映射叶子项之后启用
Sv39, QEMU 正常执行并打印 7 个数据值; pyremu 的纯 Python 路径与加速执行引擎都在
satp 生效后的首次取指处投递 InstrPageFault, 陷入 m_fail 分支打印陷态记录, 受调试
程序无法使用 1 GiB 页。

### 根因

- 纯 Python 的 `sv39_walk` 在根页表项上只调用 `_level1_next_ppn`, 该项带 R 或 X 时不
  是指向下一级页表的指针, 遍历直接返回失败。
- 加速执行引擎的 `sv39_walk` 在 `l2_pte.is_ptr == 0` 时返回 `Ok(None)`, 同一处缺失。
- `pte_assemble_pa` 与 `sv39_page_size` 只处理 level 0 与 level 1, 没有 1 GiB 页的
  页号拼接与页大小。

### 修复

- 新增 `_level1_leaf(raw, va)`, 在根页表项处先判叶子, 命中时按 1 GiB 页返回
  (PPN, 权限位) 与页大小, 置位 A 位、D 位的行为与其余两级相同。
- 加速执行引擎的 `walk_l1_leaf` 改为 `walk_superpage_leaf`, 由 level 参数选择 1 GiB
  或 2 MiB 的页号拼接, 拼接统一经 `pte_assemble_pa` 完成; `sv39_walk` 在根页表项为
  叶子时以 level 2 调用该函数。
- `pte_assemble_pa` 增 level 2 分支: PPN[17:0] 取自 VA[29:12]; `sv39_page_size`
  在 level 2 返回 1 GiB。
- `reconstruct_tlb_pa` 与 `ppn_for_tlb` 增 level 2 分支: 写入 TLB 的页号抹去
  PPN[17:0], 命中时按虚拟地址补回。

### 回归测试

- `tests/test_mem_access/test_mmu.py`: 根页表叶子项的页号、页大小与物理地址;
  同一用例在加速执行库被禁用的纯 Python 路径上重跑一遍。
- `pyremu/_native/cpu/src/mmu.rs` 的 `test_assemble_pa_1g`: PPN[17:0] 由虚拟地址覆盖,
  vpn0 参与合成, 按 4 KiB 处理时结果不同。
- `pyremu/_native/cpu/src/translate.rs` 的 `sv39_walk_accepts_1g_root_leaf` 与
  `tlb_entry_of_1g_page_reconstructs_pa`: 遍历接受根级叶子项并置位 A 位; TLB 条目命中
  时按虚拟地址还原物理地址。

### 端到端验证

裸机汇编 `sv39_giga` 在 QEMU 与 pyremu 的两种执行路径上逐字节一致, 7 个数据值相同;
`sv39_test`、`tlb_remap`、`xpage_fault` 的比对结果不变。



## 2026-11-13 — 未对齐访存按字节完成, 跨页存储的第二页缺页不写入, PMA 按区间判定

### 现象

- 同一段裸机汇编在 QEMU 与 pyremu 上的结果不同。未对齐的载入与存储落在已映射页内时,
  QEMU 按字节完成访问; pyremu 的纯 Python 路径投递 LdAddrMisaligned (4) 或
  StAddrMisaligned (6), 该指令不产生任何访存效果, 加速执行引擎则正常完成。
- 跨页的 8 字节存储在第二页缺页时, 加速执行引擎已把前 4 个字节写入第一页的物理页,
  QEMU 不修改任何内存。
- 物理地址区间越过主存或设备窗口末尾时, 纯 Python 路径不投递访问故障, 越界部分读回
  零字节; 加速执行引擎投递 Ld/StAccessFault。

### 根因

- `mem_read` / `mem_write` 在地址翻译之前判定位宽对齐并抛出 `AlignmentError`。RISC-V
  允许实现按字节完成未对齐访问, QEMU 对已映射页即如此实现。
- `write_ram_cross_page` 先写第一页的字节, 再翻译第二页; 第二页缺页时第一页已被修改。
- PMA 检查只判定访问的起始地址, 未判定整个区间的窗口归属。

### 修复

- 删除 `AlignmentError` 与两处对齐检查, 未对齐访问交由物理内存后端按字节完成。
- 跨页存储先把两页都翻译并完成 PMP 与 PMA 检查, 再按地址从低到高写入两段字节; 第二页
  缺页或越权时整次存储不修改任何内存, 陷态的 `mtval` 取第二段的虚拟地址.
  之后才依次写入第一页与第二页.
- 新增 `Bus.pma_check(addr, size)`, 按区间判定主存或同一设备窗口的归属;
  `mem_read`、`mem_write` 与取指校验改用它。

### 回归测试

- `tests/test_trap/test_mem_fault.py`: 未对齐载入与存储按字节完成的取值; 未映射页上
  未对齐载入的 `mtval` 为原始地址; 跨页存储的第二页缺页时第一页不被修改且 `mtval`
  为第二段地址。
- `tests/test_peripheral/test_bus.py`: `pma_check` 对越过主存末尾与设备窗口末尾的区间
  返回假。
- `pyremu/_native/cpu/src/hart_sched.rs` 的 `cross_page_write_second_page_fault_writes_nothing`:
  Rust 侧同一条边界。

### 端到端验证

裸机汇编 `xpage_fault` 与 `malign_fault` 在 QEMU 与 pyremu 的两种执行路径上逐字节一致:
前者的陷态成因 15、`mtval` 与物理页末尾 8 字节均相同; 后者的三条陷态记录、未对齐载入的
取值与物理页末尾 8 字节均相同。`battery` (1059 项)、`memtest`、`selfmod`、`tlb_remap`、
`sv39_test`、`load_const` 的比对结果不变。



## 2026-11-12 — linalg 载荷新增四个矩阵尺寸变体, 载荷检查移出 Makefile 配方

### 变更

`fn_apps/linalg` 原先只有默认维数 2400 的一档, 单个矩阵 43.95 MiB。现以 cargo 特征选择矩阵
维数, 特征互斥, 均未置位时取默认维数:

| 特征 | 维数 N | 单个矩阵字节数 |
|------|-------|---------------|
| `2mib` | 512 | 2.00 MiB |
| `4mib` | 725 | 4.01 MiB |
| `8mib` | 1024 | 8.00 MiB |
| `16mib` | 1449 | 16.02 MiB |
| 均未置位 | 2400 | 43.95 MiB |

- `fn_apps/Makefile` 的 `linalg` 规则在构建默认载荷之后, 依次以四个特征各构建一次, 每次构建
  后立即按尺寸改名复制为 `linalg_2m`、`linalg_4m`、`linalg_8m`、`linalg_16m`: 特征集变化时
  cargo 重编译本包, 产物路径始终是同一个文件名。`linalg` 因此从 Rust 载荷模板循环中移出,
  由一条独立规则产出默认载荷与四个变体。
- 新增 `fn_apps/check-payloads.sh`: 逐个运行载荷的检查从 `check` 配方移入该脚本, 参数为
  qemu 命令、产物目录与载荷名。脚本接收整个 `$(ALL_PAYLOADS)` 及四个变体, 输出含 `FAIL`
  即返回非 0。
- `bsp/tee_aux_tools/cache-probe-exploit/tee_ecall_regress.c` 的填充阶段跳过表中增加四个变体:
  分解的计算量随矩阵维数的三次方增长, 填充阶段会反复重跑同一批载荷。
- `fn_apps/valgrind.sh` 不变: 四个变体与 `linalg` 是同一份代码, 只差维数, 在宿主侧逐个做
  内存检查不增加覆盖。

### 验证

`make -C fn_apps linalg` 产出五个载荷, 经 `qemu-riscv64` 运行:

| 产物 | 维数 N | 单个矩阵 | max\|x - x_true\| | 结果 |
|------|-------|---------|-----------------|------|
| `bin/linalg` | 2400 | 43.95 MiB | 2.728e-11 | PASS |
| `bin/linalg_2m` | 512 | 2.00 MiB | 1.705e-12 | PASS |
| `bin/linalg_4m` | 725 | 4.01 MiB | 2.842e-12 | PASS |
| `bin/linalg_8m` | 1024 | 8.00 MiB | 4.093e-12 | PASS |
| `bin/linalg_16m` | 1449 | 16.02 MiB | 8.413e-12 | PASS |

- `sh check-payloads.sh qemu-riscv64 <fn_apps>/bin linalg linalg_2m linalg_4m linalg_8m
  linalg_16m` 返回 0, 五项均 PASS。
- `make -C bsp/tee_aux_tools/cache-probe-exploit bin/tee_ecall_regress` 在 `-Wall` 下无警告。

### 说明

- 四个变体不改变 `mem-oom-rejected` 的结果: 自退出的飞地在退出时经
  `clear_enclave_mem_region` 归还分区, 填充阶段反复创建飞地不会耗尽内存池。


## 2026-11-11 — 新增关机与复位请求设备: 受调试程序请求关机或复位时停止连续执行

### 变更

`pyremu/peripheral/power_ctrl.py` 新增 `PowerCtrl`. 控制寄存器位于偏移 0x00, 写入
`PowerRequest.SHUTDOWN` 即 0x5555 请求关机, 写入 `PowerRequest.REBOOT` 即 0x7777 请求复位;
其余取值以及其他偏移的写入被忽略。请求一经置位即保持, 由 `PowerCtrl.request` 读出。

请求置位时, 设备置位加速执行引擎的停止标志并置位唤醒事件, 使正在执行的一轮尽快退出到
Python 侧; 全部 hart 处于 WFI 等待时, 唤醒事件使该轮不再阻塞。`RunStopReason` 新增
`SHUTDOWN = 4` 与 `REBOOT = 5`; `Emulator.run` 在轮次开始前与结束后读取该设备的请求,
据请求停止并记录停止原因; 调试器的 `_handle_run_stop` 在收到这两个停止原因时报告并返回 REPL。

- `pyremu/emu/setup.py` 在 `power_base` 非 0 时注册该设备, 构造参数只传入停止标志与唤醒事件,
  不持有 `Emulator`; `power_base` 取 0 时 `Emulator.power_ctrl` 为 None。
- `mk/peripherals.mk` 新增 `POWER_BASE ?= 0x00100000`, `PeripheralConfig` 新增字段 `power_base`。
  `PlatformConfig.minimal()` 的主存从 0 开始, 该模式取 0; `--chip-dts` 模式的芯片设备树没有
  该节点, 同样取 0。
- `pyremu/utils/dev_tree/build.py` 在 `/soc` 下生成 `syscon@<base>` 节点, 其下 `poweroff` 与
  `reboot` 两个子节点分别以 `syscon-poweroff` 与 `syscon-reboot` 给出偏移 0 与两个请求取值,
  由 OpenSBI 的 `fdt_reset_syscon` 或 Linux 的 `syscon-poweroff` 经 regmap 写入。
- `pyremu/utils/counter.py` 新增顺序编号计数器 `Counter`: 每次调用返回自增前的取值, 另有
  `reset` 与 `reset_to`。设备树的 phandle 分配改用该计数器。

### 回归测试

- `tests/test_utils/test_counter.py`: 自增前的返回值, 默认起点, `reset` 与 `reset_to`。

## 2026-11-11 — CSRRS 与 CSRRC 把 mip 的外部中断线写入软件 SEIP 位

### 现象

受调试程序的内核 shell 在执行 `cd eval` 之后执行 `ls`, 没有产生任何输出, 执行不继续。
调试器读出 `mip=0x222`、`mie=0x22a`、`scause=0x8000000000000009` 即 S 外部中断,
`sepc` 落在 `handle_softirqs` 内; hart0 停在 `handle_irq_desc`, 其余 hart 停在 `do_idle`。
此时 virtio-blk 的中断状态为 0, 状态寄存器为 0x0f 即 DRIVER_OK, PLIC 的挂起寄存器为 0。
S 外部中断没有任何中断源, 却在每个指令边界重新投递, hart0 的处理函数立即返回并再次进入陷态。

### 根因

`mip` 的 bit 9 有两个来源: 存储值中的该位为外部中断线的取值, 由中断控制器同步; 软件可写的
SEIP 部分单独存放, 读出值取两者之或。

CSRRS 与 CSRRC 的语义是读出 CSR, 按 rs1 置位或清零, 写回结果。写入路径从写入值的 bit 9
取软件位, 该值由读出值算出, bit 9 含外部中断线的当前取值。外部线为高时执行
`csr_set(CSR_MIP, MIP_SSIP)` 或 `csr_clear(CSR_MIP, MIP_SSIP)`, rs1 的 bit 9 为 0, 但写入值
的 bit 9 为 1, 于是外部线被记成软件位。中断控制器撤销外部线时只写存储值, 软件位不再有清除的
路径: 受调试程序只对这些指令的 SSIP 位置位或清零, 从不写 SEIP。此后 `mip.SEIP` 恒为 1,
`mie.SEIE` 使能, S 外部中断按优先级在每次指令边界投递; PLIC 没有挂起源, 得到响应返回 0,
处理函数返回后立即再次陷态。

两个执行引擎的 CSR 写入都只接收最终值, 没有接收指令实际改写的位, 因此都产生了这一行为。

### 修复

- CSR 写入路径增加写入掩码: CSRRW 为全部位, CSRRS 与 CSRRC 为 rs1。`mip` 的软件可写位与
  软件 SEIP 位都按掩码写入; 掩码不含 bit 9 时软件位保持不变。
- 纯 Python 执行路径: `Hart.write_csr` 增加 keyword-only 参数 `write_mask`, 默认 `None`
  表示全部位, 调试器与测试的整值写入不受影响; `_sys_csr` 按指令类型给出掩码,
  `_write_mip` 用它限定可写位并决定是否更新软件 SEIP 位。
- 加速执行引擎: 新增 `csr_write_masked`, `csr_write` 以全部位调用它; `handle_csr` 按 funct3
  给出掩码。

回归测试:

- `tests/test_trap/test_interrupt.py::TestMipWriteMask` 的四个用例
- `pyremu/_native/cpu/src/csr.rs` 的 `csrs_mip_ssip_does_not_latch_software_seip`、
  `csrc_mip_ssip_does_not_latch_software_seip`、`csrw_mip_clears_software_seip`、
  `csrs_mip_seip_sets_software_seip`


## 2026-11-11 — 模拟器与 RISC-V 特权规范不符的多处行为

### 现象

对照 RISC-V 特权规范核对模拟器的行为, 发现下列与真实硬件不符之处。纯 Python 执行路径与
加速执行引擎各自存在其中的一部分, 同一行为在两侧的取值也不完全一致:

1. `mip.SEIP` 的写入被整体忽略, 软件位与外部中断线没有分开保存; `mip.USIP`、`mip.UTIP`
   与 `mip.UEIP` 可被 `csrw mip` 置位, 规范规定这三位只读。
2. `sync_pending_interrupts` 强制置位 `mie.MSIE`, 改变受调试程序写入的中断使能。
3. WFI 在 `mip.MSIP` 挂起而 `mie.MSIE` 未置位时退出等待; 规范只要求已使能的中断唤醒。
4. 进入陷态时自动清除 CLINT 的 msip 与 `mip.MSIP`、`mip.SSIP`, 而规范要求由陷态处理函数
   清除中断源。
5. `sstatus` 视图包含 `MPRV`, 且不提供只读的 `UXL`。
6. `mstatus.SD` 作为可写存储位参与读写, 而不是按 FS、VS、XS 是否为 3 在读出时算出。
7. MRET 与 SRET 返回低于 M 模式时不改变 `MPRV`。
8. `mepc` 与 `sepc` 不按 IALIGN 约束低位, `mtvec` 与 `stvec` 接受保留的 MODE 编码,
   `misa` 的写入被接受。
9. RV64 上可访问仅 RV32 存在的 CSR, 包括计数器 CSR 的高半部分与 `*h` 系列寄存器。
10. `mstatus.TSR` 与 `mstatus.TVM` 未生效: S 模式执行 SRET、访问 `satp`、执行 SFENCE.VMA
    都不触发非法指令。
11. M 模式忽略全部 PMP 条目; 锁定条目应同样约束 M 模式, 且条目锁定后 `pmpcfg` 与
    `pmpaddr` 应拒绝写入。
12. PMP 的执行权限检查同时要求 R 位; 规范只要求 X 位。
13. Sv39 页表遍历不置位页表项的 A 位与 D 位。

### 根因

CSR 与陷态处理按简化模型实现: 挂起位全部当作可写存储位、陷态入口承担了中断源撤销、
`mstatus` 的派生位当作普通位保存; WARL 约束与 TVM、TSR 门控没有实现。PMP 的检查把
M 模式整体放行, 并在执行权限上沿用了读取的 R 位要求。页表遍历只做读取与权限判定,
没有实现硬件对 A 位与 D 位的置位。两个执行引擎各维护一份实现, 上述行为在两侧同时存在,
或只在其中一侧存在。

### 修复

- `mip` 的写入只改变 SSIP 与 STIP 的存储值; 软件写入的 SEIP 另存, 读出值为该软件位与
  外部中断线的或; USIP、UTIP 与 UEIP 保持只读。
- 删除 `sync_pending_interrupts` 中对 `mie.MSIE` 的强制置位。
- WFI 的唤醒条件取 `mip & mie`, 不设 MSIP 例外。
- 陷态投递不再清除 CLINT 的 msip 与 `mip.MSIP`、`mip.SSIP`; IMSIC 的认领路径照旧由
  软件经 MTOPEI、STOPEI 回应。两个引擎同步。加速执行引擎的 `sync_msip` 在旧有 PLIC 模式下
  按 CLINT 的 msip 电平同步 `mip.MSIP`, 电平为 0 时清除该位; 原先只置位不清除, 陷态投递
  不再代为清除后, 固件写 0 确认的 IPI 会反复投递, 使 hart 停在 M 模式的中断处理中。
- `sstatus` 掩码去掉 `MPRV`, 加入 `UXL`; 读出时 `UXL` 恒为 2, `SD` 由 FS、VS、XS 算出,
  两者的写入被忽略。
- MRET 与 SRET 在目标特权级低于 M 时清除 `MPRV`。
- `mepc` 与 `sepc` 的写入按 IALIGN 清低位; `mtvec` 与 `stvec` 的 MODE 取 2 及以上时
  忽略写入; `misa` 的写入被忽略。
- RV64 上访问仅 RV32 存在的 CSR 触发非法指令。
- S 模式访问 `satp`、执行 SFENCE.VMA 在 `mstatus.TVM=1` 时, 执行 SRET 在
  `mstatus.TSR=1` 时触发非法指令。
- PMP 在 M 模式下只忽略未锁定的条目; 锁定的条目按权限位检查。条目锁定后对 `pmpaddr`
  的写入、以及组内任一锁定条目存在时对该组 `pmpcfg` 的写入都被忽略。
- PMP 的执行权限只检查 X 位。
- Sv39 页表遍历在每一级置位 A 位, 写访问在叶子项上置位 D 位; 置位所需的物理写入先经
  PMP 检查, 被拒绝时按原访问的类型投递访问故障。调试器的只读查询不置位。
