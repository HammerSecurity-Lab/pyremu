# 2026-10 修复与变更记录

## 2026-10-29 — 测试固件的启动 hart 选择

### 现象

`tests/test_preempt.py` 的部分用例随机失败, 捕获到的 `scause` 为 12 (InstructionPageFault);
`tests/test_trap/test_stack_overflow.py::TestStackOverflowUmode` 的控制台输出每个字符重复三次,
`fib(5)=5` 与 `Fault caught` 都不出现。

### 根因

`kernel.s` 与 `u_mode_run_fib.s` 的 `_start` 不读 `mhartid`: 复位后全部 hart 的 PC 都是入口地址,
每个 hart 都完整走一遍 M 模式引导。`kernel.elf` 只有一个调度器、一份 `process_table` 与一份
U 模式栈, 多个 hart 并发引导互相覆盖页表与进程状态, U 模式取指落入未映射页;
`u_mode_run_fib.elf` 的每个 hart 各写一遍 UART 并各读一次输入, 输出的每个字符因此出现三次,
单一 hart 拿不到完整输入。

### 修复

两份固件的 `_start` 首条指令改为 `csrr t0, mhartid`, `mhartid` 非零时跳入 `park_hart` 的
WFI 循环, 只有 hart 0 继续引导。ELF 经 `make -C tests build-multi build-s2u -B` 重建。
回归测试: `tests/test_preempt.py` 的全部用例恢复默认多 hart 装配;
`tests/test_multihart.py::TestMultiHartBoot::test_non_boot_harts_park` 断言非启动 hart 保持
M 模式且 PC 停在 `park_hart` 区间内;
`tests/test_multihart.py::TestMultiHartBoot::test_boot_hart_boots_to_smode` 断言启动 hart 进入
S 模式。


## 2026-10-29 — 单步执行在全部 hart 处于 WFI 等待时永久阻塞

### 现象

逐周期驱动固件的调用方在固件进入 WFI 自旋之后不再返回: `tests/test_lottery_boot.py` 的全部
用例超过 10 秒超时, 调试器的 `run N` 命令同样停住。

### 根因

`RunOps.step()` 在末尾对全部等待的 hart 调用 `_wfi_sleep_if_idle`。该函数按最早到期的定时器
与运行超时截断等待上限, 两者都不存在时上限为 None, `_wake_event.wait(None)` 只由外设活动
唤醒。`run()` 在调用前设置运行超时, 上限因此有限; 单步执行没有运行超时, 于是继承了这一不受
限的等待, 而单步调用方期望立即拿回控制权。

### 修复

`step()` 不再发出空闲等待, 全部 hart 等待时直接返回 0。阻塞改由 `run()` 的纯 Python 轮次
`_run_one_round` 在全部存活 hart 处于等待时调用; 加速执行路径原本就在 `_native_finalize`
中调用, 保持不变。回归测试见
`tests/test_emulator.py::TestWfiIdleSleep::test_step_does_not_block_when_all_harts_wait` 与
`tests/test_emulator.py::TestWfiIdleSleep::test_pure_python_round_sleeps_when_all_harts_wait`。


## 2026-10-22 — 栈帧记录解码器的负偏移未作符号扩展

### 现象

调试器扫描陷态入口的存栈指令时, `sd x1, -16(sp)` 被识别为偏移 4080。按该偏移读取的地址
位于 sp 之上 4 KiB 处, 返回地址取自错误的地址, 栈回溯在该帧给出错误的结果。

### 根因

`pyremu/core/decoder.py` 的 `decode_sd_sp` 以 `(imm << 52) >> 52` 作 12 位符号扩展。该移位
作用于非负的 Python 整数, 结果仍为非负数, 符号位不参与扩展; `pyremu/utils/disassem.py` 中
的同名函数同样如此。调用方 `_parse_trap_save_offsets` 把返回值与 sp 相加, 该返回值应为
有符号偏移。

### 修复

两处均改为判定 12 位立即数的符号位, 置位时减去 0x1000, 返回 [-2048, 2047] 范围内的有符号
偏移。回归测试见
`tests/test_disasm.py::TestDecodeSdSp::test_negative_offset_is_sign_extended`。


## 2026-10-11 — S 模式陷态帧的存放位置与返回目标判定

### 现象

飞地打印的一行陷态记录中, sepc 指向陷态入口自身的存栈指令 `sd s1, 0x48(sp)`, stval 落在该指令
与页边界的交点上: 陷态入口在保存陷阱帧时二次触发了页错误, 真正的故障现场被这一次次生故障覆盖,
不可复原。该行之后 hart 驻留在挂起路径的 WFI 之内。

### 根因

- S 模式之内发生的陷态把陷阱帧存放在被中断的 S 模式栈上, 帧基址取陷入前的 sp 减 264。陷入前的
  sp 落在未映射区间之内时, `SAVE_CONTEXT` 的第一条存栈指令即触发页错误; 该错误再次进入同一个
  入口, 记录中只剩下这一次次生故障;
- 返回路径以帧内偏移 256 的槽位取值是否为 0 判定本次陷态是否来自 S 模式: S 模式路径在该槽位写入
  0, 用户态路径写入用户 sp。帧改存于临时栈之后, 两条路径在该槽位写入的都是陷入前的 sp, 该判定
  不再成立; 返回 S 模式时按该判定走入用户态分支, 还会把 sscratch 写成帧的末端, 破坏「S 模式之内
  sscratch 为 0」这一约定, 使下一次陷态被按用户态陷态处理。

### 修复

- `bsp/sittim/src/entry.s`: `save_kern_ctx` 的帧末端取陷入前的 sp 与 `tmp_stack_top` 中的较小
  者; 该值小于 `tmp_stack + 264` 时取 `tmp_stack_top`。帧因此始终完整落在临时栈之内, 不再依赖
  被中断的 sp 指向可写内存;
- `bsp/sittim/src/entry.s`: 两条陷入路径一律把陷入前的 sp 写入帧内偏移 256 的槽位。返回分支改读
  `sstatus.SPP`: 取 1 时以帧内该槽位恢复 sp 并保持 sscratch 为 0, 取 0 时先把该槽位写入
  sscratch, 再经交换恢复 sp。sstatus 在 `RESTORE_CONTEXT` 之前读取;
- `bsp/sittim/src/trap.rs`: `TrapGprs` 的字段 `usp` 更名为 `sp_before_trap`, 取值为陷入前的 sp:
  陷态来自 U 模式时是用户 sp, 来自 S 模式时是该模式的 sp; 陷态详情的输出一并更名。
